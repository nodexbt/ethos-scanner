## 1. Security

### S1. HIGH — Supabase tables have no row-level security (except two)
`scripts/migrations/*.sql`: only `scan_jobs` and `notifications` enable RLS. `investigations`,
`investigation_edges`, `allowed_users`, `allowed_users_audit`, `profile_latest`, `profile_addresses`,
`watchlist`, `scan_quota`, `monitoring_runs` do not. The app only uses the service key, so today this is
latent, but any holder of the project's anon key (which Supabase issues to every project and which the
Credible Audiences work plans to share a data layer with) can read and write every table through PostgREST.
Fix: `alter table … enable row level security` on every table, no policies. The service role bypasses RLS,
so nothing in the app changes.

### S2. HIGH — Critical advisories on `next` 16.2.9 and `next-auth` 4.24.14
`npm audit --omit=dev`: 2 critical, 2 high. Next: RCE in the image optimisation API (SVG/AVIF), cache
poisoning, SSRF in rewrites. next-auth: OAuth state/PKCE cookies not bound to the provider. `npm audit fix`
resolves all of them. Also `postcss` and `sharp` high.

### S3. HIGH — The public share endpoint returns the raw stored row
`app/api/share/[shareId]/route.ts:31` returns the whole `InvestigationRow`, so `clusterResult.logs`
(which name every wallet the scan touched), `clusterResult.usage` (admin-only in the UI,
`result-header.tsx:119`) and `twitterEvidence` go to anyone with the link, with `Cache-Control: public`.
Fix: project an explicit public DTO; strip `logs`, `usage`, `twitterEvidence`, `id`.

### S4. MEDIUM — Any signed-in user can write 4 MB of arbitrary JSON into any investigation
`app/api/investigations/route.ts:151-194` (`POST`, twitter evidence) checks neither ownership nor the
`TWITTER_SEARCH_ENABLED` flag. The content is not rendered in the UI any more, but it is embedded verbatim
into the "slash report" prompt in `lib/evidence-export.ts:50-61` that investigators paste into an LLM,
so it is a stored prompt-injection channel, and it is served publicly via S3. Fix: require owner or admin,
gate on the feature flag, validate the shape (`{ [address]: { tweets: [{url, author}] } }`), and cap
per-address entries.

### S5. MEDIUM — Access eligibility is frozen into the JWT for 30 days
`app/api/auth/[...nextauth]/route.ts:115-124` snapshots score, human-verification and validator count at
sign-in; the re-check at 130-142 and `requireAuth` (`lib/auth.ts:38-43`) both read those stale token
values. Only the allowlist arm is live. A user whose score drops below 1800, or whose verification is
revoked, keeps access until the session expires (NextAuth default 30 days). Fix: re-fetch the Ethos
profile in the `jwt` callback when `token.ethosCheckedAt` is older than, say, an hour, or read the live
score from `profile_latest`.

### S6. MEDIUM — Public profile pages publish the link graph of scans their owners believe are private
`lib/public-profile.ts:50` loads `scan-p<id>` without an `is_public` check and `app/p/[handle]/page.tsx:127-146`
renders every linked profile with name, handle, score and confidence, each linking onward, so the whole
edge graph is crawlable without a session (throttled only by `revalidate = 120`). The share dialog
meanwhile says "This scan is private" (`share-dialog.tsx:142`). This is a deliberate product decision per
the README, but the promise and the behaviour disagree. Pick one: counts only for unshared scans, or fix
the copy.

### S7. LOW — No Content-Security-Policy
`next.config.ts:52-60` sets nosniff, frame-deny and referrer policy but no CSP. The only inline script is
the constant theme snippet, so a nonce-free CSP with `script-src 'self' 'sha256-…'` is feasible.

### S8. LOW — Rate limiting is per-instance memory
`lib/rate-limit.ts` (acknowledged in its comment). The share endpoint is the only user; share ids have
114 bits of entropy so enumeration is not a real risk. Fine to leave, but do not reuse it for anything
that matters.

### S9. LOW — Unguarded `req.json()` in `POST /api/scan`
`app/api/scan/route.ts:31`: malformed JSON throws → 500 with a stack in logs. Also `target` has no length
cap before `parseScanInput`. Other routes do this correctly.

### S10. LOW — CSRF relies entirely on `SameSite=Lax`
No origin check on any mutating route. NextAuth's cookie defaults make this safe today; worth an
`Origin`/`Sec-Fetch-Site` check in `requireAuth` for mutating methods before automation adds API keys.

Checked and fine: X attestation by immutable user id (not handle); the server owns scan results; job
polling is owner-scoped; `safeCallbackUrl` prevents open redirects; `safeExternalUrl` on every external
href; PostgREST filter sanitisation; share ids are CSPRNG; admin via env only; service key never reaches
the client; no SSRF vector in `parseScanInput` (host allow-list, no fetch of user-supplied URLs).

## 2. Pipeline correctness (`lib/cluster-scanner.ts`, `lib/alchemy.ts`, `lib/ethos.ts`)

### P1. HIGH — The first-funding transfer is counted twice
`cluster-scanner.ts:317-331` collects every native sender as a "shared incoming sender"; the cleaning step
at 702-706 removes only contracts, and labelled exchange hot wallets are explicitly skipped (688) but not
removed. `scoreCandidate` (398-418) then adds `shared_incoming_sender` (+5) on top of
`shared_exchange_funder` (+5) or `shared_first_funder` (+8). Two unrelated users who both withdrew their
first Base ETH from the same Coinbase hot wallet reach 10 points and two signal types → **Possible**.
`docs/scoring.md` says the exchange case alone is below threshold and that incoming senders exclude
exchanges. Fix: skip `getAddressLabel(from)` in `incomingSources` and remove the first funder from
`sharedFunders` before scoring.

### P2. HIGH — `funded_by_cluster` (auto-Strong) fires for wallets not in the results
`cluster-scanner.ts:781-783` tests the funder against `allCandidateAddrs`, the per-chain discovery set
(every profile wallet with one direct transfer), not the wallets that scored. Target tips X once; X once
gas-funded Y; Y once sent the target a token → Y is **Strong**, "first funded by another wallet in the
results", which is false. Fix: compute this in a second pass over candidates that passed the threshold.

### P3. HIGH — Stargate routers pass as exchanges; the "EOA-only" destination filter is a no-op
`cluster-scanner.ts:884, 901, 1582` use `!label.includes("Bridge")` while `isExchangeAddress`
(`known-addresses.ts:117`) also excludes Stargate and Across; the two Stargate routers (96-97) are labelled
"Stargate". Two wallets that both bridged via Stargate get `shared_cex_deposit` (+8). At 839
`contractCache.get(to)` is almost always empty for destinations, so DEX routers and the Ethos contracts
consume the 60 verification slots first. Fix: use `isExchangeAddress` in all three places; run
`batchIsContract` over shared destinations before verifying.

### P4. MEDIUM — One profile can appear twice (Strong and Possible)
`:1240-1241` dedupes the two tiers separately; signals from a profile's second wallet never merge into
the first. Fix: dedupe the union, then split.

### P5. MEDIUM — Sub-threshold per-chain scores are dropped before the cross-chain merge
`:796` filters at 8 per chain; 5 on Base plus 5 on Ethereum never becomes 10. Contradicts
`decisions.md` "signals add up". Fix: keep `score > 0`, threshold after merge.

### P6. MEDIUM — Multi-hop candidates are Possible at 6 points, below the documented 8 floor
`:1449, 1458-1459` hard-code `medium`. Fragile: any later `recalcConfidence` would drop them.

### P7. MEDIUM — Several failure paths return empty data instead of marking the scan degraded
Target history cap (`:537`, no `onCapped`, no coverage note); candidate fetch (`:651-656`, no `onFailure`);
`getFirstFunder` and `getIncomingTransfers` (`alchemy.ts:150-161, 316-317`) collapse HTTP errors to
`null`/`[]`; `fetchProfilesByAddresses` (`ethos.ts:172-173`) treats an unexpected 200 body as "no
profiles" and does not call `onBatchError`, so a result with every candidate filtered out is saved as
complete over a good one. This is exactly the failure the degraded guard exists to prevent.

### P8. MEDIUM — Unhandled rejection in the job runner's flush ticker
`lib/scan-runner.ts:75-92`: `flush` awaits `updateScanJob` with no catch inside `setInterval`. One
Supabase hiccup becomes an unhandled rejection in the `after()` worker; the job then sits until the
6-minute stale sweep. Wrap in try/catch; same for the final status writes at 107 and 119.

### P9. MEDIUM — Transfers de-duplicated by `tx.hash`
`alchemy.ts:284-293`: a swap (native out + token in, same hash) or any multi-transfer tx collapses to one
row. Key on Alchemy's `uniqueId`.

### P10. MEDIUM — No timeouts on any external fetch
`alchemy.ts:97, 355`, `ethos.ts` (six calls), `twitter-search.ts:74`. A hung socket stalls a chain
forever while the heartbeat keeps the job "running". Add `signal: AbortSignal.timeout(20_000)`.

### P11. MEDIUM — Ethos bulk-lookup fallback is a 500-call sequential retry storm
`ethos.ts:150-170`: on a 429 it calls `fetchProfile` per address with no backoff.

### P12. LOW
Multi-hop race can push one profile twice (`:1439-1481`); pre-score filter at `:620-634` is dead code
(threshold 3 with weight 4); `mergeSignalsInto` re-admits zero-score signals into `signalTypes` (`:478`);
`t.to.toLowerCase()` crashes on contract-creation rows (`alchemy.ts:190`); retried calls are billed in
`usage` (`alchemy.ts:96`); `candidateFirstFunders.find(() => true)` is `[0]`; comments jump step 4 → 7.
Memory: ~200 candidates × 2 directions × 15k full transfer objects × 5 chains held until the end
(unverified in practice, but likely gigabytes on a heavy target).

### Docs vs code
| `docs/scoring.md` / `decisions.md` says | Code does |
|---|---|
| incoming senders exclude exchanges | included (P1) |
| `funded_by_cluster` = already in the cluster | any discovery-set wallet (P2) |
| Possible = score ≥ 8 | multi-hop at 6 (P6) |
| signals add up across chains and wallets | sub-8 dropped per chain first (P5) |
| one entry per profile | tiers deduped separately (P4) |

| any failure marks degraded | first-funder, candidate and Ethos-shape failures silent (P7) |

## 3. Backend code quality

- **Seven ad-hoc in-memory caches** (allowlist, profile names, verified list, stats, baseline, network,
  rate-limit buckets), each hand-rolled with its own TTL. One `ttlCache(key, ttl, loader)` helper would
  remove ~80 lines and make the serverless caveat live in one place.
- **Whole-table walks on every cache miss**: `getInvestigationStats` and `fetchVerifiedInvestigationRows`
  (`investigations.ts:189-375`) and `getNetworkOverview` (`network.ts:31-40`) page the entire table into
  memory per instance per minute. Fine at 5k rows; not at 50k (which batch mode will produce). Move to
  SQL: a `sum()` RPC, a join against `profile_latest.human_verified`, and `group by` for the network view.
- **No generated database types**: every module hand-maps rows with `as` casts (`toJob`, `rowToUser`,
  `toSummary`). `supabase gen types typescript` would catch column drift at compile time.
- **Session typing via eight `@ts-expect-error`s** instead of a `types/next-auth.d.ts` module augmentation.
- **`fetchAttestedProfile` runs twice per login** (`signIn` and `jwt` callbacks): two Ethos API calls.
- **Quota is consumed before the job row is created** (`scan/route.ts:55-73`); a failed insert burns a
  scan. Streaming clients that have an active job get a 202 JSON they cannot parse (line 47).
- `getInvestigation` and `getInvestigationByShareId` duplicate the row mapping.
- `lib/db/investigations.ts` (758 lines) mixes list queries, caches, save rules and sharing.

## 4. Frontend

### F1. MEDIUM — The existence check spends a scan on any non-2xx
`scan-provider.tsx:246`: `r.ok` false for 401/403/500/network → starts a scan for an investigation that
exists. Only 404 should mean missing.

### F2. MEDIUM — Resumed scans restart the progress bar at 0%
`scan-log.tsx:44-62` anchors on mount and ignores `progress.elapsed`. After a reload an 80% scan says
"0% · ~2m left".

### F3. MEDIUM — Re-scan hides the previous result for the whole job
`scanner-view.tsx:136` nulls `loaded` while a job runs; `ResultView` already has a `scanning` prop that
nobody passes.

### F4. MEDIUM — Accessibility
Compact scan input has no label and an icon-only submit (`scan-input.tsx:27-38`); the live log announces
every line (`scan-log.tsx:128-130`, should be `aria-live="off"` with a separate `role="status"` for stage
changes); log level is colour-only; toggles lack `aria-pressed` (`scans-list.tsx:219`, `watch-button.tsx:46`);
`decrypted-text.tsx:385` exposes the scrambled string to screen readers and re-scrambles every 30 s
regardless of reduced motion; quota tooltip is on a non-focusable span (`app-header.tsx:107`).

### F5. MEDIUM — No `error.tsx`, `not-found.tsx` or `loading.tsx`; whole-app client auth gate
`app-shell.tsx:17-34`: every page is a spinner until `useSession` resolves; `notFound()` shows Next's bare
screen. A `proxy.ts` session check would stop unauthenticated visitors downloading the app shell.

### F6. LOW — Polling and perf
`setJob` fires every 1.5 s because `data.progress` is always truthy (`scan-provider.tsx:167`), re-rendering
every context consumer; lost-contact after 7.5 s (`:136,155`) is shorter than a deploy; `/p` calls
`getPublicProfileSummary` twice per render (`page.tsx:24,45`, wrap in `cache()`); the landing page is a
client component for two animations; three.js ships on every route including `/p` and `/s`
(`background.tsx:10`), the captured PNG is never redone on resize, and light mode applies a permanent
`filter: invert()` to a fixed oversized layer.

Checked and fine: Radix dialogs (focus trap, escape, title/description); the route-owns-result refactor
aborts stale loads correctly; `params` typed as promises per Next 16; external hrefs are safe.

## 5. Design and UX

### D1. HIGH — Public surfaces present certainty the app refuses to
`/p` leads with a red "2 strong links" and an alert icon (`page.tsx:87-111`); "Evidence, not a verdict"
lives only in OG metadata; the disclaimer is last. `/s` has no `generateMetadata`, so the unfurl is the
generic site card. These are the pages people screenshot.

### D2. HIGH — Confidence tiers are shown everywhere and explained in one place
Pills appear in the header, link list, `/p`, Network, notifications; the only explanation is a footnote at
the bottom of the evidence dialog. `STRONG_RULE` in `scan-utils.ts:202` exists for this and is unused.
Put it in a tooltip on `ConfidencePill` and a one-line legend under "Linked profiles".

### D3. MEDIUM — Coverage notes are nearly invisible; degraded handling is good
`DegradedBanner` has a `coverage` prop that is never passed; notes sit behind a `text-xs` toggle at the
bottom of the header card (`result-header.tsx:201-220`); `/p` computes the count and never shows it.
"No on-chain links found" with 200-counterparty caps silently in force is a misleading read.

### D4. MEDIUM — The strongest evidence is one click away
Rows show only `reasons[0]` (`link-list.tsx:45-48`). Inline the top signal's `detail` sentence for strong
rows so the first screen answers "why is #1 strong".

### D5. MEDIUM — Landing-page tone contradicts the product
"the cleanest smoking gun there is", "Signals that don't happen by accident", "Reputation you can verify"
(`landing-page.tsx:145-258`) is verdict language; the app, `/p` and the disclaimer say the opposite. The
fake-terminal demo also doesn't match the card UI it leads to.

### D6. MEDIUM — The dither background costs more than it gives on content pages
Four separate mitigations exist for one decoration: the landing overlay, the `Plate` component, every
Card's blur, the footer's blur. Keep the animation for landing and sign-in; use a static CSS texture
elsewhere (the unused `--dot-*` tokens in `globals.css` suggest that was once the plan).

### D7. LOW — Gaps in states and mobile
Network view has no empty state for a fresh install; `/s` collapses a 429 into "Not Found"; the evidence
dialog's "Scan X" fires without a quota warning while `NotScannedYet` does warn; quota and user name are
hidden under 640 px; `site-header.tsx:39` hides the only CTA on phones; `/follows` uses emerald found
nowhere else.

## 6. What this means for automation

The pieces automation needs mostly exist, but each has a gap that will bite once scans run without a
person watching:

1. **The job system is tied to the HTTP request.** `after()` runs inside the same Vercel invocation
   (`maxDuration = 300`), there is no queue, no retry, and stale jobs are only detected when someone polls.
   A scheduler needs either a real queue (Supabase `pg_cron` + a worker route, or GitHub Actions like the
   mirror) or a sweeper that re-queues stale jobs. P8 (unhandled rejection) and P10 (no timeouts) are the
   two things most likely to strand an unattended job.
2. **Identity.** Quota and ownership are keyed by Ethos profile id. `saveInvestigation` already supports
   `scannedByProfileId: null` for automated scans, and `scan-verified.ts --owner=` exists, but there is no
   service identity for API calls. Before exposing anything to a cron or an external caller, add an API-key
   path to `requireAuth` (and the origin check in S10) rather than reusing a person's session.
3. **Trust the saved result before you act on it automatically.** P1–P3 inflate Possible and Strong on
   Base; P7 lets a half-failed scan save as complete. Notifications (`notifyNewLinks`) and the edge graph
   already consume these without a person in the loop. Fix the three HIGH pipeline bugs and the degraded
   paths first, or automation will amplify false positives into watchers' inboxes.
4. **Scale the reads.** The whole-table walks in section 3 and the per-instance caches will not survive
   batch mode. Move aggregates into SQL now, while the tables are small.
5. **Lock the database.** S1 (RLS) before the Credible Audiences data layer lands in the same project.
